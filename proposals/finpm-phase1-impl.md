# 一期实现说明：金石 FinPM 插件（完整四环节）

> 配套《立项书：金石 FinPM》v4 ｜ 本文只讲"怎么做"，不讲"为什么做"（后者见立项书）。
>
> 状态：实现草案 v1 ｜ 日期：2026-06

---

## 1. 一期范围

里程碑一 = **完整四环节编排层**，全部以 Claude Code 插件（skill）形态实现，端到端产出 PRD：

```
研究员 ──brief──→ 主持人 ──台账(初选)+草图──→ 质询者 ──台账(已批准)──→ 书记员 ──→ PRD
环节1            环节2                      环节3                   环节4
```

- 不自建 agent harness（LLM 调用、工具、上下文、子 agent 隔离全部用 Claude Code 现成的）。
- 编排层守 harness-agnostic 纪律：表达为"数据 + 规则"，平台耦合只留薄胶水。
- 产出的 PRD **按指定模版**走（团队/公司现成模版，不另造）。

---

## 2. 文件结构

```
assets/                       # 规则 / 资产层（领域 IP，平台无关）
  decision-list.md            # 决策清单：依赖排序的决策点 + 域标签
  challenge-rubric.md         # 四视角挑刺量规
  prd-template.md             # 指定 PRD 模版 + 决策→章节映射规则
skills/                       # 编排层（薄胶水，挂在 Claude Code 上）
  fin-research/SKILL.md       # 研究员（环节1）
  fin-brainstorm/SKILL.md     # 主持人（环节2）
  fin-challenge/SKILL.md      # 质询者（环节3，subagent 隔离）
  fin-compile/SKILL.md        # 书记员（环节4）
work/<需求名>/                # 工作产物（每个需求一个目录）
  sources/                    # 原始材料库，一源一文件
    reg-2026-001.md           #   含 URL + 抓取日期 + 原文摘录
    competitor-A.md
    user-feedback-Q2.md
  brief.md                    # 结构化简报（消化后，每条 → sources 引用）
  ledger.md                   # 决策台账 ← 系统中心
  design-draft.md             # 设计思路稿
  sketches.md                 # ASCII 交互草图
  challenge-log.md            # 挑刺记录
  prd.md                      # 最终 PRD（按指定模版）
```

`assets/` 是跨需求复用的领域资产；`work/<需求名>/` 是单个需求的全部产物。两者都是纯文件系统——二期独立产品换成数据库/对象存储时，逻辑结构照搬。

## 3. 四个 skill 的输入输出契约

每个 skill = 一个角色，**人显式调用、不自动编排**。契约用"只读哪些文件、写哪些文件"表达，这就是 harness-agnostic 的规格——二期换 runtime，契约不变。

| skill | 角色 | 只读 | 产出 | 关键约束 |
|---|---|---|---|---|
| `fin-research` | 研究员 | 需求描述、信源清单 | `sources/*`、`brief.md` | 边抓边落盘到 sources（防上下文爆）；brief 每条带 sources 引用；不下产品结论 |
| `fin-brainstorm` | 主持人 | `brief.md`、`decision-list.md` | `ledger.md`(初选)、`design-draft.md`、`sketches.md` | 六步对话；只提问呈现不替人选；每屏带引用或"推测"标注 |
| `fin-challenge` | 质询者 | `ledger.md`、`sketches.md`、`brief.md`、`challenge-rubric.md` | `ledger.md`(已批准)、`challenge-log.md` | **subagent 隔离**：全新上下文，读不到脑暴对话；只攻击决策结果；审批回到人 |
| `fin-compile` | 书记员 | `ledger.md`(已批准)、`prd-template.md` | `prd.md` | 只汇编不创作；按映射规则填模版；台账与 PRD 漂移时报告而非擅改 |

## 4. 决策清单（decision-list.md）结构

**不用域做主结构**——域只用作标签。骨架是依赖排序的决策点流：

```markdown
## D-01 业务定性与牌照路径
- 域: [合规]
- 核心: 是
- 依赖: —
- 追问提纲: 本业务是否触及放贷/支付/征信牌照？挂靠还是自营？...
- 常见候选: A 助贷(不碰放贷牌照) / B 自营(需牌照) / C 联合贷

## D-03 资金方模式
- 域: [资金, 合规]          # 跨域 → 多标签
- 核心: 是
- 依赖: D-01               # 必须先定 D-01
- 追问提纲: 单一资金方还是联合贷？出资比例？...
- 常见候选: A 单一持牌机构 / B 联合贷 / C 自有资金
```

- **依赖**字段决定主持人逐项初选的顺序（拓扑序），不是按域分组。
- **域**是可多值标签，只服务两件事：完整性扫描（每个监管面是否都覆盖）、挑刺视角路由（合规视角 ↔ 带"合规"标签的决策）。
- "按域分组展示" 只是主持人收敛时的一个视图，不是底层结构。
- 一期 v1 先覆盖 **合规路径 + 资金流** 两个面的决策点（约 8–12 个），后续迭代补全。

## 5. 决策台账（ledger.md）格式

人类可读的结构化 markdown，每个决策一个块；文件头放进度计数。

```markdown
# 决策台账 · <需求名>
进度: 已批准 6 / 已决待审 2 / 暂缓 1 / 讨论中 1

## D-04 资金托管方式
- 状态: 已批准          # 讨论中 / 已决待审 / 已批准 / 暂缓 / 已失效
- 域: [资金, 合规]
- 候选: A 银行存管 / B 持牌支付备付金
- 选择: A
- 理由: 立项期合规稳定优先
- 证据: brief.md §1.5 → sources/reg-2026-001.md
- 挑刺记录: 质询者质疑对账时效 → 人维持 A，补充对账方案（见 challenge-log #3）
- 审批: 2026-06-14 人确认
```

纯 markdown 的理由：人能直接改、git 能版本管理、二期产品能解析。一期不引入 YAML/数据库；若未来要机读，给状态字段套一段 ```yaml 即可，但非必要。

## 6. 角色隔离：subagent + 文件契约

质询者必须读不到脑暴过程，否则会为主持人引导出的方案辩护。一期用 **subagent 实现隔离**：

- 进入环节 3 时，`fin-challenge` 起一个 subagent，**全新上下文**，prompt 明确"你只能读 `ledger.md / sketches.md / brief.md / challenge-rubric.md`，不得读任何对话历史"。
- subagent 对每个"已决待审"决策跑：追问 → 四视角挑刺 → 给严重度和依据，写入 `challenge-log.md`。
- **审批不在 subagent**：挑刺结果交回人，人修订或坚持，人显式确认才置"已批准"。

> **机制 vs 规格**：subagent 是一期的隔离机制（Claude Code 给真正的全新上下文）；可迁移的规格是那条**只读文件契约**（质询者输入 = {ledger, sketches, brief, rubric}）。二期独立产品用"自己的全新 LLM 调用"实现同一契约，机制随平台换、契约不变。

可选增强（一期可不做）：四视角各起一个独立 subagent 并行挑刺，互不软化。一期先单 subagent 顺序跑四视角即可。

## 7. PRD 模版与映射（prd-template.md）

- 模版是**指定的**（团队现成 PRD 模版），书记员适配它，不另造一套结构。
- 文档里维护一套 **决策 → 章节映射规则**，例如：

```
D-01 业务定性     → PRD §1 产品定位 / §6 合规依据
D-02 营销合规     → PRD §6 合规依据 / §4 交互(年化明示)
D-04 资金托管     → PRD §5 资金流 / §6 合规依据
sketches.md       → PRD §4 交互与展示（ASCII 草图直接嵌入）
```

- 书记员只把"已批准"决策按映射填进模版对应章节；未批准的决策不进 PRD（完整性门控）。

## 8. 证据链：三级物理可追溯

```
ledger.md (决策)  →  brief.md (论断)  →  sources/xxx.md (原文 + URL + 抓取日期)
```

每一跳都是能打开的文件。抽查某条监管引用时，从台账一路点到 sources 原文，验证是否幻觉。引用抽查通过率是核心度量。

## 9. 一期内部开发顺序

| 迭代 | 周 | 做什么 | 验证 |
|---|---|---|---|
| 迭代1 · 心脏 | W1–5 | 主持人 + 质询者（环节2+3）+ 决策清单 v1（合规+资金）+ 台账格式；brief 先手工喂 | 决策质量：挑刺改选率、辩护测试 |
| 迭代2 · 两头 | W6–9 | 研究员（环节1，产 sources+brief）+ 书记员（环节4，按模版汇编 PRD）；四环节首次成线 | 证据率；PRD 盲评（问出来 vs 生成） |
| 迭代3 · 打磨 | W10–13 | 决策清单补全；失效检测与回流；端到端跑真实需求 | 端到端耗时；失效拦截率 |

迭代1 brief 手工喂是临时占位（研究员尚未做），不影响心脏环节的决策质量验证；迭代2 研究员上线后 brief 转自动产出。

## 10. harness-agnostic 自检清单

每加一个编排能力，过一遍：

- [ ] 它表达成"数据 + 规则"了吗？（清单/量规/台账/映射 = 文件，不是写死的 prompt 流程）
- [ ] 角色边界是"只读哪些文件"的契约，而不是依赖某个 Claude Code 专有机制？
- [ ] 换个 runtime，这套逻辑能照搬吗？
- [ ] 是不是为了实现它必须 hack Claude Code？—— 若是，记下来，这是毕业信号。
